# 4. 通过二进制分析内存泄漏故障的方案调研

本章关注三类通过二进制或运行期探针分析内存泄漏的方案：静态二进制扫描、动态二进制插桩和 eBPF 内核追踪。调研内容分为两部分：一部分来自工具文档、项目源码和已有研究资料，另一部分来自 Linux 服务器上的统一 Benchmark 实验。

本轮实验对 BinAbsInspector 和 Ghidra 做了独立的静态二进制分析验证，对 Dr. Memory 保留工具调研。静态实验与动态 Benchmark 分开记录：BinAbsInspector 和 Ghidra 的风险条目、函数路径和符号化结果用于评价静态定位能力，不直接转换为动态工具的 `detected_blocks`、`detected_bytes`、precision 或 recall。统一 Benchmark 实测覆盖 Valgrind Memcheck、LSan、heaptrack 和 BCC memleak，其中 LSan 与 heaptrack 的结果作为横向基线，帮助说明不同观测路线在真实运行中的差异。

## 4.1 静态二进制扫描

静态二进制扫描在程序启动前处理可执行文件、共享库和反编译后的中间表示。分析器沿着控制流和数据流追踪分配结果，检查某条路径上是否缺少对应的释放操作。它不依赖特定测试负载，常用于构建完成后的检查、发布前审计，以及缺少源代码的程序分析。

静态工具看到的是程序“可能走过”的路径，无法还原某次运行中的实际内存状态。报告可以指出某个分支存在分配后未释放的风险，却无法直接说明一次运行创建了多少对象、对象存活了多久。静态扫描结果应作为风险线索，后续再用代码审查、动态复现或专项测试确认。

### 4.1.1 BinAbsInspector

BinAbsInspector 面向二进制程序做静态分析，建立在 Ghidra 等二进制分析基础设施之上，使用抽象解释、控制流分析和数据流分析检查缺少源代码或难以重新编译的程序。它的输出重点是潜在的内存安全风险位置，属于运行前的风险分析，无法直接提供运行期泄漏统计。

在内存泄漏问题上，BinAbsInspector 可以围绕分配函数、指针传递和释放函数检查资源流。调研时重点关注四类线索：分配返回值是否能到达释放函数；异常分支、提前返回和错误处理是否跳过释放；指针跨函数传递后是否可能丢失唯一引用；同一资源是否存在多条释放路径。本次在 Linux test server 上使用与 Ghidra 10.1.2 配套的 BinAbsInspector 版本对 benchmark 的三种 ELF 进行了 headless 验证。带调试信息和去调试信息版本均成功完成分析并输出 25 条 CWE 风险记录，完全 strip 版本输出 44 条。

它的输出一般落到函数、指令或源码位置，并附带相关调用路径、触发条件和规则匹配结果。这些结果说明某条路径存在风险，是否构成真实泄漏还要看程序的资源管理语义。当前发布版本的检查器覆盖多类内存安全和输入验证问题，但没有 CWE-401 内存泄漏专项检查器。因此，本轮结果证明它可以用于潜在风险路径发现和地址级定位，不能直接给出 benchmark 的泄漏 blocks/bytes。报告中把 25 条或 44 条记录作为静态风险条目数，单独于动态泄漏规模统计。

### 4.1.2 Ghidra

Ghidra 是开源的逆向工程和二进制分析框架，提供反汇编、反编译、函数识别、控制流图、调用图和脚本扩展能力。它更像一套通用分析平台，不会直接生成完整的内存泄漏报告；泄漏分析依赖分析脚本、检查规则和人工复核。

分析内存分配问题时，通常先定位 `malloc`、`calloc`、`realloc`、`new` 及其封装函数，再识别 `free`、`delete` 或自定义释放函数。随后对照反编译结果和控制流图，检查异常分支、循环、跨函数返回和资源所有权传递。脚本可以批量提取函数调用关系、分配点和可能的资源流转路径。

Ghidra 的输出主要是反编译位置、调用关系、控制流路径和人工复核线索。遇到符号缺失、间接调用、线程同步或自定义分配器时，分析结果需要结合汇编细节判断。它不会自动给出运行期泄漏对象数和字节数。本轮已用 Ghidra 12.1.2 对带调试信息、去调试信息和完全 strip 的 ELF 做默认 headless 分析，并用脚本提取函数数量、关键函数命中情况和调用关系；它作为静态分析平台单独评价，不纳入动态工具 runner。

### 4.1.3 检测原理与输出形式：识别潜在泄漏路径

静态扫描从分配点开始，沿控制流和数据流检查资源是否能到达释放操作。若一条路径经过分配，却无法证明释放一定发生，工具会标记疑似泄漏路径。报告通常包含风险位置、分配点到风险位置的调用或控制流路径、可能触发问题的分支，以及风险类型或置信度。

这一输出能回答“哪里值得检查”和“风险怎样产生”，无法直接回答“实际泄漏了多少对象”。所以静态结果应单独记录为潜在路径命中，不能和动态工具的 detected_blocks、detected_bytes 混用。

### 4.1.4 能力边界与调研结论

静态分析能覆盖测试没有执行到的路径，这是它相对动态工具的价值。代价是，二进制程序中的间接调用、函数指针、跨线程传递、引用计数、自定义内存池和条件释放都会让资源是否最终释放变得难以判断。分析器无法证明程序行为时，往往会采用保守规则，误报也随之增加。

对静态方案的评价应关注潜在路径覆盖率、人工确认率、误报率和定位可读性。precision 和 recall 只有在真实缺陷集合可确认时才有意义，报告条目数不能代替实际泄漏对象数。此次调研得到的结论是：BinAbsInspector 更接近规则化的二进制风险扫描，Ghidra 更接近可扩展的人工分析平台；两者都需要动态实验确认实际泄漏规模。

## 4.2 动态二进制插桩

动态二进制插桩在程序运行时改写或翻译目标指令，并在内存访问、函数调用、分配和释放附近注入监测逻辑。工具通常无需重新编译被测程序，就能记录运行期的内存事件、调用栈和对象状态。Valgrind Memcheck 和 Dr. Memory 是这一方向的代表方案。

这类工具记录的是实际执行过的路径。一次测试运行中发生了哪些分配和释放、哪些地址仍处于占用状态，都可以从运行期记录中还原；测试没有覆盖的代码路径则不会出现在结果里。

### 4.2.1 Valgrind Memcheck

Valgrind Memcheck 通过动态二进制翻译执行目标程序，同时维护一份与应用内存相对应的影子内存（shadow memory）。它追踪堆内存的分配和释放，同时检查非法访问、未初始化值、重复释放、释放后使用，以及进程结束时仍然存在的堆对象。

Memcheck 根据对象地址、引用关系和释放状态，对仍可达或已经失去引用的对象进行分类，并报告泄漏块数量、字节数和调用栈。标准分配器、调试符号和调用栈信息较完整时，报告可以定位到较细的分配路径。它的主要限制来自运行开销，程序中的每条指令都可能经过翻译和检查。

### 4.2.2 Dr. Memory

Dr. Memory 是基于动态二进制插桩框架的内存调试工具。它在不修改源代码的情况下运行目标程序，检查内存访问、未初始化数据、释放后使用、重复释放和内存泄漏。

工具在运行期维护内存状态，程序结束或检查阶段输出诊断报告。它与 Valgrind Memcheck 的基本思路相近，但底层插桩框架、平台支持、报告字段和分配器兼容性存在差异。Dr. Memory 本轮没有纳入 Linux 服务器实验，因此这里只保留工具调研结论，不延伸出具体性能数据。

### 4.2.3 检测原理与输出形式：记录运行期内存事件、释放关系和调用栈

动态插桩直接记录分配、释放和访问事件，再依据地址、大小、线程和调用栈维护对象状态。测试结束时，工具可以给出实际运行中的对象数量、字节数和泄漏分类，例如 definitely lost 或 possibly lost。

这条路线的证据来自真实执行过程，地址级配对通常较完整。调用栈能否解析到函数名和源码位置，仍取决于符号文件、编译选项、内联优化和运行环境。

### 4.2.4 工程特征与实测观察

动态插桩的成本主要来自指令翻译、影子内存维护、事件记录和调用栈收集。它常用于开发调试、线下回归、故障复现和小规模泄漏确认，长期在线运行会受到明显的性能压力。

本轮在 Linux test server 上用统一 Benchmark 对 Valgrind 执行了 5 次 `high_freq_no_leak` 重复实验。裸 Benchmark 的 workload 平均耗时为 0.34 ms；Valgrind 下同一指标为 78.91 ms，相对放大约 235 倍；runner 平均耗时为 1498.60 ms。这个结果说明，Valgrind 的高精度来自完整的运行期检查，同时也说明它更适合线下精检。该数据来自固定负载，不能直接外推到所有程序。

## 4.3 eBPF 内核追踪

eBPF 追踪把观测逻辑加载到 Linux 内核，通过内核中的安全执行环境追踪用户态函数、系统调用、内核函数或进程事件。用户态内存泄漏的常见做法是在目标进程的 `malloc`、`free` 或分配器内部函数上挂载 uprobes，捕获分配地址、大小、线程和调用栈，再用 BPF map 保存中间状态。

这类方案对目标程序改动较少，通常无需重新编译应用。它只处理选定事件，运行开销通常低于动态插桩；结果会受到挂载点、内核版本、BTF 或符号信息、权限、采样策略和用户态汇总程序影响。输出也往往是周期性快照，而非完整的对象生命周期报告。

### 4.3.1 BCC memleak

BCC memleak 用于观察用户态内存分配。典型用法是在目标进程的分配和释放函数上挂载 uprobe，记录分配地址与大小，再按调用栈或栈 ID 聚合 outstanding allocation。

工具在观察窗口内周期性输出仍未释放的对象数量、字节数和主要调用路径。这个结果更像某一时点的分配快照：对象在快照前已经释放，可能不会出现在输出中；对象仍被缓存分配器持有，也可能被记录为 outstanding allocation。

### 4.3.2 bpftrace

bpftrace 是面向 eBPF 的高级追踪语言和工具，通过脚本观测 uprobes、uretprobes、tracepoints、kprobes 等事件，并使用聚合 map 输出计数、字节数、调用栈和分布信息。

在内存泄漏调研中，脚本可以在分配函数返回时保存地址、大小、线程或调用栈，在释放函数执行时删除对应记录，最后统计仍保留的条目。它的探针组合和聚合方式比 BCC memleak 灵活，但配对逻辑、过滤规则、状态清理和输出格式都要自行设计。bpftrace 本轮没有单独纳入统一 runner，相关判断来自工具文档和脚本模型分析。

### 4.3.3 检测原理与输出形式：在内核态追踪分配、释放和调用路径

eBPF 路线先选择分配和释放探针，再在内核态记录地址、大小、线程、时间戳和 stack ID，并通过 BPF map 维护 outstanding 状态。用户态程序按时间窗口读取 map，生成分配次数、释放次数、未释放对象数、未释放字节数和调用栈聚合结果。

这一路线的输出口径取决于采样时点和探针覆盖范围。周期性快照反映的是“此时仍被追踪的对象”，不能单独证明对象长期未释放；短生命周期对象、未命中的内部路径和分配器缓存都可能改变结果。

### 4.3.4 能力边界与实测观察

eBPF 的观测范围取决于所选函数和采样范围。分配器内部路径较深时，应用请求可能经过线程缓存、arena 或其他内部层；只挂在外层函数，返回值、实际分配大小和释放事件可能与内部行为不一致。采样能降低处理成本，也可能漏掉短生命周期对象。内核态聚合的调用栈还可能受到符号、栈深度和编译优化影响。

本轮 BCC 实验出现了一个很明确的边界。`growth_leak` 在 1 线程、2 线程下的预期值分别为 2000 blocks / 128000 bytes 和 4000 blocks / 256000 bytes，但 3 次重复实验的最终观测值却各自稳定在 1332 blocks / 85248 bytes 和 2664 blocks / 170496 bytes。前 3 个快照尚能观察到增长趋势，后续快照则停止增加；双线程结果约为单线程的两倍。这一现象更像是长时间分阶段追踪中遇到了观测上限，因此不能简单地将其解读为业务泄漏量仅含 1332 或 2664 个对象。

在开启 frame pointer 的构建中，BCC 对 `DefiniteLeakPath`、`GrowthLeakPath` 和 `MixedLeakPath` 各重复 3 次，分别得到 4000 / 256000、4000 / 256000 和 800 / 64400，均与 Benchmark 真值一致。原始栈中可以看到对应的泄漏函数名，说明编译选项和栈采集方式会直接影响 eBPF 的路径定位效果。

## 4.4 三类方案横向比较

这三类方案观察的是程序的不同层面。静态扫描看控制流和数据流，动态插桩看实际执行过的指令和对象状态，eBPF 看被选中的运行期事件和周期性状态。它们给出的证据粒度不同，不能用一个指标直接排出优劣。

| 对比维度 | 静态二进制扫描 | 动态二进制插桩 | eBPF 内核追踪 |
| --- | --- | --- | --- |
| 代表方案 | BinAbsInspector、Ghidra | Valgrind Memcheck、Dr. Memory | BCC memleak、bpftrace |
| 检测位置 | 二进制文件、反编译结果、控制流和数据流 | 目标进程运行期的指令、内存访问和分配事件 | 内核态 eBPF 程序，对用户态函数或系统事件挂探针 |
| 主要观测对象 | 潜在分配路径和释放路径 | 实际执行的分配、释放、访问和对象状态 | 被选中的分配/释放事件和 outstanding 快照 |
| 泄漏规模量化 | 难以直接给出真实对象数和字节数 | 可给出一次运行中的对象数和字节数 | 可给出快照时点的对象数和字节数，受采样和挂点影响 |
| 调用栈与路径 | 调用图、控制流路径、反编译位置 | 运行期调用栈和分配路径 | stack ID、内核聚合调用栈或用户态符号化结果 |
| 配对精度 | 依赖静态路径推断，别名和间接调用会降低置信度 | 通常较高，能依据运行期地址和对象状态配对 | 取决于探针覆盖、采样策略、地址复用和状态维护 |
| 误报/漏报来源 | 路径不可判定、规则保守、语义缺失 | 未覆盖的运行路径、符号缺失、分配器支持差异 | 快照时点、短生命周期对象、缓存分配、事件丢失 |
| 运行开销 | 分析阶段开销，目标程序无需运行 | 较高，指令翻译、影子内存和事件记录会增加成本 | 较低，但栈采集、map 更新和输出窗口仍有成本 |
| 权限与部署 | 读取二进制和调试信息 | 需要以工具方式启动目标程序 | 通常需要较高系统权限和匹配的内核能力 |
| 适用场景 | 发布前审计、潜在路径发现、无源码分析 | 线下复现、精确确认、回归测试 | 在线筛查、趋势观察、热点发现和长期采样 |

### 4.4.1 检测位置与观测对象

静态扫描发生在程序运行前，处理可执行文件和库中的结构信息，能覆盖未执行路径，但得到的是程序逻辑的近似模型。动态插桩跟着目标进程运行，看到的是本次负载实际触发的事件。eBPF 位于内核观测层，只采集指定函数或事件，覆盖范围由探针和内核能力决定。

静态报告说明某条路径存在风险，动态插桩报告说明某次运行中出现了具体对象状态，eBPF 快照说明某个观察时点仍有一批被追踪对象未释放。三种结果的证据强度和时间范围不同，读取时不能混为一谈。

### 4.4.2 泄漏规模量化能力

没有运行输入时，静态分析很难给出实际泄漏对象数和字节数。动态插桩根据运行期地址和大小汇总对象数量与字节数，适合生成可复现的检测真值。eBPF 也能输出这些字段，但数字对应采样窗口内的观测状态，解释时要结合快照时间、采样方式和目标分配器。

统一 Benchmark 应把“潜在路径命中”和“实际对象/字节数匹配”分开统计。静态方案记录是否识别到真实泄漏路径；动态和 eBPF 方案还可以记录 detected_blocks、detected_bytes、precision 和 recall。

### 4.4.3 调用栈与路径定位能力

静态工具给出控制流路径、调用图或反编译位置，便于追踪潜在的责任调用链。动态插桩记录分配发生时的调用栈，再结合符号信息定位到函数名和源码行。eBPF 常用 stack ID 或栈聚合 map 保存路径，结果的可读性取决于栈深度、符号化过程和应用编译方式。

报告至少要区分三个层级：只保留原始地址；能符号化到函数名或源码位置；能按调用栈聚合对象数量和字节数。有调用栈字段不等于具备完整定位能力，栈可读性、聚合粒度和归属准确性应分别记录。

### 4.4.4 配对精度、误报风险与缓存干扰

动态插桩在分配和释放事件发生时维护对象状态，地址级配对能力较强。静态扫描依赖路径推理，遇到间接调用、跨线程传递和复杂资源所有权时，结果更容易停留在“可能泄漏”。eBPF 也能维护地址级状态，但实际效果会受到观测点、采样策略、事件丢失和地址复用影响。

内存分配器的缓存机制需要单独留意。线程缓存、arena 和运行库内部保留的内存，在应用层释放后仍可能留在分配器内部。如果采集点位于较低层级，工具可能把这部分状态报告为 outstanding allocation。解析时应优先使用 Benchmark 相关调用栈筛选业务分配；无法明确归属的内容放入 notes，不能直接计入检测结果。

### 4.4.5 运行开销、权限要求与部署条件

静态分析消耗离线分析时间和机器资源，目标程序在分析期间无需运行。动态插桩会直接放大目标进程的运行开销，对时延和吞吐敏感的程序影响更大。eBPF 的在线成本较低，但加载探针、维护 BPF map、采集调用栈和输出快照仍会消耗资源。

部署条件也不同。静态分析需要可读的二进制、库文件和调试信息；动态插桩需要能够以工具方式启动目标程序，并满足架构、库和权限要求；eBPF 追踪依赖 Linux 内核支持、BPF 能力和足够权限，部分场景还需要 root 或等效能力。工程比较中应记录重新编译要求、运行权限、平台适配、安装复杂度和结果保存方式。

## 4.5 二进制分析方案的能力边界与适用场景

选型时先看要回答的问题。发布前检查关注“哪里可能有风险”，静态扫描更合适；测试环境要确认一次真实泄漏，Valgrind Memcheck 或 Dr. Memory 更直接；服务运行期间想观察增长趋势和热点路径，BCC memleak 或 bpftrace 的侵入更小。

静态方法的主要问题是误报和规模量化不足。动态插桩的限制来自运行开销和测试覆盖范围。eBPF 的结果容易受采样窗口、探针覆盖、权限条件和缓存分配影响。后续实验应把检测精度、路径定位、运行开销和部署条件放在同一评价框架中，同时写清楚每个方案实际观测到的内容。

本章的调研和实测放在一起看，可以得到一个比较具体的判断：静态二进制扫描负责发现潜在路径，动态二进制插桩负责线下确认对象状态，eBPF 内核追踪负责运行中的筛查和趋势观察。三条路线的输出口径不同，后续比较时应同时记录检测原理、输出效果、运行开销、权限要求和适用场景。

这些结论为第五章的方案对比矩阵提供分类依据，也为统一 Benchmark 的 case 设计和评价指标定义限定了范围。
