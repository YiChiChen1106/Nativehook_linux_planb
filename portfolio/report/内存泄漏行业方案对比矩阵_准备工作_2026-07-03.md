# 内存泄漏行业方案对比矩阵准备工作

日期：2026-07-03

## 1. 本阶段目标

7 月 9 日组会前，先完成“行业方案对比矩阵”的准备工作，不急着写完整调研报告。矩阵要支撑后续《内存泄漏故障感知和轻量化采集分析调研报告》中“行业内存泄漏检测/判定算法对比”这一节。

本阶段重点回答三个问题：

1. 业界有哪些主流内存泄漏检测路线？
2. 每类路线依赖什么观测信号来判定泄漏？
3. 哪些路线适合在线、低开销、二进制侧采集，能够和当前 native_hook/Plan B 工作衔接？

## 2. 检索边界

优先检索：

## 3. 第一批候选来源

### 3.1 动态二进制检测：Valgrind Memcheck

- 来源：Valgrind User Manual / Memcheck。
- 链接：https://valgrind.org/docs/manual/manual.html
- 补充链接：https://valgrind.org/docs/manual/valgrind_manual.pdf
- 关键信息：
  - Memcheck 支持详细 leak checking。
  - 常见泄漏类别包括 definite、indirect、possible、reachable。
  - 优点是精度高、报告详细、适合开发测试阶段。
  - 主要局限是运行开销高，官方文档示例说明程序可能慢 20-30 倍并使用更多内存。
- 对本项目的意义：
  - 可以作为“高精度但重开销”的行业基准。
  - 适合和 native_hook 的“轻量化采集”形成对比。

### 3.2 运行时 Leak Sanitizer：LLVM LeakSanitizer / AddressSanitizer

- 来源：LLVM Clang LeakSanitizer documentation。
- 链接：https://clang.llvm.org/docs/LeakSanitizer.html
- 关键信息：
  - LeakSanitizer 是运行时内存泄漏检测器。
  - 可与 AddressSanitizer 结合，也可 standalone。
  - 文档说明 LSan 在进程结束前通常几乎没有额外性能开销，但结束时会有额外泄漏检测阶段。
- 对本项目的意义：
  - 代表“编译/链接期接入 + 运行时扫描”的路线。
  - 强项是测试阶段准确性；弱项是通常需要重新编译或链接运行时，不适合作为完全透明的二进制侧常驻采集。

### 3.3 动态 instrumentation：Dr. Memory

- 来源：Dr. Memory 官方站点与 leak 文档。
- 链接：https://drmemory.org/
- 泄漏文档：https://drmemory.org/page_leaks.html
- 论文：Practical Memory Checking with Dr. Memory, CGO 2011。
- 论文链接：https://ieeexplore.ieee.org/document/5764689
- 关键信息：
  - 支持 Windows、Linux、Mac。
  - 可检测 uninitialized memory、unaddressable memory、use-after-free、double free、memory leaks 等。
  - 泄漏报告包括 leaks、possible leaks、still-reachable allocations，并默认收集分配调用栈。
- 对本项目的意义：
  - 代表“动态 binary instrumentation + 调用栈报告”的路线。
  - 能支撑报告里对“二进制分析能做什么”的论述。

### 3.4 静态分析：Clang Static Analyzer / CodeQL / Infer

- 来源：Clang analyzer unix.Malloc checker。
- 链接：https://clang.llvm.org/extra/clang-tidy/checks/clang-analyzer/unix.Malloc.html
- 来源：CodeQL CWE coverage for C/C++。
- 链接：https://codeql.github.com/codeql-query-help/cpp-cwe/
- 来源：Infer 官方站点。
- 链接：https://fbinfer.com/
- 关键信息：
  - Clang unix.Malloc checker 跟踪 malloc/free，检查 memory leaks、double free、use-after-free。
  - CodeQL 对 CWE-401 覆盖了 memory may not be freed、memory never freed、realloc 失败泄漏等查询。
  - Infer 支持 C/C++/Objective-C，检查 null dereference、memory leaks、coding convention 等。
- 对本项目的意义：
  - 代表“不运行程序、从源码路径推断泄漏”的路线。
  - 优点是能覆盖未执行路径，适合 CI/代码审查。
  - 局限是依赖源码/构建信息，对运行时真实行为、三方库、长期增长趋势观测不足。

### 3.5 学术静态算法：Saber / Full-Sparse Value-Flow Analysis

- 论文：Static Memory Leak Detection Using Full-Sparse Value-Flow Analysis。
- 作者：Yulei Sui, Ding Ye, Jingling Xue。
- 会议：ISSTA 2012。
- 链接：https://yuleisui.github.io/publications/issta12.pdf
- ACM 链接：https://dl.acm.org/doi/10.1145/2338965.2336784
- 关键信息：
  - Saber 面向 C 程序内存泄漏静态检测。
  - 基于 sparse pointer analysis 和 sparse value-flow graph 追踪 allocation 到 free site 的值流。
- 对本项目的意义：
  - 可作为报告中“静态 value-flow 判定算法”的学术代表。
  - 和 native_hook 的运行时采集路线形成互补：静态分析偏路径推断，native_hook 偏运行中真实行为观测。

### 3.6 低开销采样检测：SWAT / Adaptive Statistical Profiling

- 论文：Low-Overhead Memory Leak Detection Using Adaptive Statistical Profiling。
- 作者：Matthias Hauswirth, Trishul M. Chilimbi。
- 会议：ASPLOS 2004。
- DOI：https://doi.org/10.1145/1024393.1024412
- 可访问页面：https://sape.inf.usi.ch/publications/asplos04.html
- PDF：https://web.stanford.edu/class/archive/cs/cs295/cs295.1086/papers/p156-hauswirth.pdf
- 关键信息：
  - 目标是把性能 profiling 中的 sampling 思想用于程序正确性检查。
  - 使用 adaptive profiling，按代码段执行频率反向调整采样率，以改善低频代码覆盖。
  - 实现工具 SWAT，用于低开销内存泄漏检测。
- 对本项目的意义：
  - 是“轻量化采集”最重要的论文代表之一。
  - 可支撑 sample/filter/batch 这类策略不是拍脑袋，而是行业长期使用的低开销观测思想。

### 3.7 eBPF / uprobe 在线检测：BCC memleak

- 来源：iovisor/bcc memleak.py。
- 链接：https://github.com/iovisor/bcc/blob/master/tools/memleak.py
- man page：https://www.mankier.com/8/bcc-memleak
- Debian man page：https://manpages.debian.org/unstable/bpfcc-tools/memleak-bpfcc.8.en.html
- 关键信息：
  - memleak 用 eBPF/bcc 打印 outstanding allocations 和 call stacks。
  - 支持用户态 libc allocation functions，也支持内核 allocation/free 路径。
  - 参数支持 sample rate、min/max allocation size、older-than threshold、top N 等。
  - Debian man page 明确提醒：对高频 alloc/free 进程 tracing 时可能引入明显 overhead。
- 对本项目的意义：
  - 与 native_hook 最接近：都是运行时、二进制侧、面向 malloc/free 事件。
  - 可作为“在线低侵入检测”的行业参照。
  - 也说明高频路径开销依然是核心问题，和当前 Plan B 的 hot-path ablation 结果能接上。

### 3.8 栈聚合与可视化：Memory Flame Graphs

- 来源：Brendan Gregg, Memory Leak and Growth Flame Graphs。
- 链接：https://www.brendangregg.com/FlameGraphs/memoryflamegraphs.html
- 补充：Flame Graphs overview。
- 链接：https://www.brendangregg.com/flamegraphs.html
- 关键信息：
  - 用 stack traces 展示内存增长或泄漏对应的代码路径。
  - 关注“哪个调用路径负责内存使用增长”，而不是只报告单个地址。
- 对本项目的意义：
  - 可作为报告中“泄漏效果分析/定位输出”的重要参考。
  - 当前 native_hook 已有 malloc/free record 和 metadata，但尚未完整覆盖 stack unwind；这正好可以作为后续能力差距。

### 3.9 GC 语言增长检测：Cork

- 论文：Cork: Dynamic Memory Leak Detection for Garbage-Collected Languages。
- 链接：https://dl.acm.org/doi/10.1145/1190215.1190224
- 补充 PDF：https://hiper.cis.udel.edu/lp/lib/exe/fetch.php/courses/other-memleak-jump.pdf
- 关键信息：
  - 面向 garbage-collected languages。
  - 通过 full-heap collection 时的 heap summary / type growth 发现持续增长对象。
  - 更适合解释“单纯未 free 之外，泄漏还可以表现为长期增长和对象可达但不再有用”。
- 对本项目的意义：
  - 作为扩展背景即可，不作为 C/C++ native heap 主线。

## 4. 第一版对比维度

| 维度 | 说明 |

## 5. 第一版行业方案矩阵骨架

| 类别 | 代表 | 检测/判定原理 | 优点 | 局限 | 和本项目关系 |
|---|---|---|---|---|---|
| 动态二进制检测 | Valgrind Memcheck | 运行程序，跟踪内存读写与 malloc/free；退出时按 definite/possible/reachable 等类别报告泄漏 | 精度高，报告细，适合开发测试 | 开销很高，不适合常驻在线 | 作为高精度基线，用来说明轻量化必要性 |
| 运行时 sanitizer | LeakSanitizer / ASan | 拦截或记录分配，进程结束时做泄漏检测 | 测试阶段易集成，准确性较好 | 依赖编译/链接 sanitizer runtime，偏测试场景 | 作为“需要构建配合”的对照 |
| 动态 instrumentation | Dr. Memory | 动态 instrumentation 检测内存错误和泄漏，报告 allocation callstack | 跨平台，报告丰富 | 仍属于调试工具，运行开销和环境依赖较强 | 支撑“二进制分析 + 调用栈归因”的可行性 |
| 静态分析 | Clang Static Analyzer / CodeQL / Infer | 不运行程序，从源码路径、异常路径和值流推断未释放资源 | 可进 CI，能看未执行路径 | 依赖源码/构建信息，误报/漏报，需要人工 triage | 作为前置筛查路线，与运行时采集互补 |
| 学术静态 value-flow | Saber | 构建 full-sparse value-flow graph，追踪 allocation 到 free 的值流 | 算法性强，适合写“判定算法” | 工程落地复杂，对动态行为覆盖有限 | 作为静态算法代表 |
| 低开销采样 | SWAT | adaptive statistical profiling，采样内存事件并估计泄漏 | 面向低开销监测，适合长运行程序 | 采样带来概率性漏报，结果需要统计解释 | 直接支撑 sample/filter/batch 的轻量化论证 |
| eBPF/uprobe | BCC memleak | 对 malloc/calloc/realloc/free 等函数挂 uprobe，记录 outstanding allocations 和 call stacks | 可附着运行中进程，侵入较低 | 高频 alloc/free 仍可能开销明显；allocator/debug symbol 依赖 | 与 native_hook 最接近，是在线二进制侧路线参照 |
| 栈聚合可视化 | Memory Flame Graphs | 聚合 allocation stack traces，展示内存增长来源 | 定位直观，适合汇报和故障分析 | 依赖栈采集质量；本身不是完整检测器 | 可作为本项目后续输出形态参考 |
| GC 语言增长检测 | Cork | 基于 GC 时 heap summary/type growth 找长期增长对象 | 适合解释“增长型泄漏” | 不直接对应 C/C++ malloc/free | 作为背景，不放主线 |

## 6. 组会推荐讲法

7 月 9 日组会可以先讲：

> 我先把行业内存泄漏检测路线按“静态分析、动态二进制检测、编译期 sanitizer、低开销采样、eBPF/uprobe 在线追踪”分成几类。它们的共同核心是找到 allocation 到 release 之间的缺口，但判定依据不同：有的是退出时可达性，有的是源码路径和值流，有的是运行中 outstanding allocations，有的是长期增长趋势。我们的 native_hook/Plan B 更接近运行时二进制采集路线，优势是可以围绕高频 malloc/free 路径做 sample、filter、batch 等轻量化控制；当前差距是 stack unwind、mmap/munmap、真实 OpenHarmony entry 和语义验证还没有补齐。
