# 3. 业界应用内存泄漏检测（判定）算法调研

本章调研面向 C/C++ 应用的 native heap 内存泄漏检测方案，重点比较四类常见路线：基于分配/释放配对的动态检测、基于编译期插桩的检测、基于运行时追踪的检测，以及基于 heap profiling 的画像分析。比较内容包括检测信号、判定时机、输出形式、调用栈定位能力、运行开销和适用场景。

需要先区分“检测到分配事件”和“判定为内存泄漏”。一个工具可以记录 `malloc` 和 `free`，但最终仍要依据对象是否持续存活、是否失去引用、是否在观察窗口内保持 outstanding，或是否形成持续增长趋势来做判断。不同工具的输出因此具有不同的时间范围和证据强度。后续统一 Benchmark 会分别记录对象数量、字节数、调用栈和运行开销，避免只依据报告中是否出现“leak”字样评价工具效果。

## 3.1 基于分配/释放配对的动态检测

基于分配/释放配对的动态检测在程序运行过程中记录堆对象的创建和释放。每次分配通常关联对象地址、申请大小、线程信息和分配调用栈；每次释放根据地址查找对应对象并更新其状态。程序结束或检查阶段，工具将仍处于活动状态的对象分类，并据此输出泄漏报告。

这类方案的核心证据来自实际运行过程。它能够回答“本次负载执行期间创建了哪些对象、哪些对象最终仍未释放”，也可以保留较完整的对象级信息。测试未执行到的路径不会出现在结果中，因此检测覆盖率依赖测试负载。对于自定义分配器、线程缓存和运行库内部保留内存，还需要结合工具的拦截范围解释结果。

### 3.1.1 Valgrind Memcheck

Valgrind Memcheck 通过动态二进制翻译运行目标程序，在执行过程中维护与应用内存对应的影子状态，并检查内存访问、初始化状态以及堆对象生命周期。Memcheck 的内存检查范围包括非法读写、使用未初始化值、释放后使用、重复释放和泄漏检查。其动态翻译和影子内存机制是高精度检查能力的主要来源[[1]](https://doi.org/10.1145/1250734.1250746)。

在泄漏检查中，Memcheck 会在程序退出时从一组可识别的根引用出发，分析仍然存在的堆块是否还能被程序引用。报告通常区分 `definitely lost`、`indirectly lost`、`possibly lost` 和 `still reachable` 等类别。`definitely lost` 表示工具无法从根引用到达该对象，通常是最明确的泄漏线索；`still reachable` 表示对象在退出时仍可达，它可能来自全局缓存、单例对象或运行库保留状态，不能直接等同于故障泄漏[[2]](https://valgrind.org/docs/manual/mc-manual.html#mc-manual.leaks)。

Memcheck 的输出通常包含泄漏分类、对象数量、总字节数、分配调用栈和汇总位置。只要目标程序带有调试信息，调用栈就可以进一步解析到函数名和源码行。对于需要确认一次具体泄漏的线下测试，它可以提供较完整的证据链：分配位置、对象大小、对象数量和退出时的存活状态。

### 3.1.2 检测效果与工程特征

这类动态检测适合做高精度基线。它能够量化一次运行中的对象数和字节数，便于与 Benchmark 中预先定义的 ground truth 对照，也便于计算 precision 和 recall。它的主要限制来自运行开销和路径覆盖：动态翻译、影子内存、每次事件的状态维护和调用栈处理都会增加程序运行成本；测试没有覆盖的分配路径也不会进入报告。

Valgrind 更适合开发调试、线下故障复现、回归测试和最终确认。它通常不适合直接放在高频业务路径上长期运行。报告解析时还应区分真正的泄漏分类与仍可达对象，避免把 `still reachable` 或运行库内部对象直接计入业务泄漏量。

## 3.2 基于编译期插桩的检测

基于编译期插桩的检测在构建阶段向目标程序加入检查逻辑，或者链接对应的检测运行库。程序运行时，插桩代码和运行库共同记录内存操作、对象元数据和调用栈；在进程退出或显式检查点，工具再根据对象的存活状态完成泄漏判定。

这类方案的优势在于能利用编译器掌握的函数边界、调试信息和运行时元数据，接入方式也比较适合持续集成和测试构建。代价是通常需要重新编译或重新链接，产物、启动方式和运行环境会发生变化，因此它更偏向测试版本和开发阶段。

### 3.2.1 ASan 与 LSan 的职责区分

AddressSanitizer（ASan）主要检测越界访问、释放后使用、重复释放等内存安全错误。LeakSanitizer（LSan）专门负责内存泄漏检测，可以和 ASan 一起使用，也可以通过 `-fsanitize=leak` 单独启用。两者经常一起出现，但检测目标不同：ASan 关注访问是否合法，LSan 关注进程结束或检查点时仍然存在的对象是否已经失去有效引用[[3]](https://www.usenix.org/conference/atc12/technical-sessions/presentation/serebryany); [[4]](https://clang.llvm.org/docs/LeakSanitizer.html)。

LSan 通常通过分配器拦截和编译/链接阶段加入的运行时支持保存分配信息，并在泄漏检查阶段扫描线程栈、全局区域和寄存器等可能的根引用。若某个对象无法从这些根引用到达，LSan 会将其报告为泄漏。这个过程更接近“退出时可达性分析”，它关注的是对象最终是否仍可达，不要求把每一条分配和释放事件完整输出给用户。

### 3.2.2 输出形式与判定特点

LSan 的典型输出包括泄漏字节数、对象数量、分配调用栈以及汇总后的泄漏位置。对同一分配路径产生的多个对象，工具通常将它们聚合成一条或少数几条报告。带有调试信息时，报告可以定位到函数名和源码行号；缺少符号时，则可能只保留地址或经过裁剪的调用栈。

LSan 的判定结果受根引用扫描和运行时语义影响。全局缓存、线程本地存储、分配器缓存或故意延迟释放的对象，可能在检查时仍然可达。长生命周期对象也可能被保留到进程退出，单次退出检查难以单独证明它属于持续增长型泄漏。因此，LSan 适合确认“测试结束时仍无法解释的对象”，对于运行期间的增长趋势，还需要额外的周期性采样或多轮负载实验。

### 3.2.3 工程特征

LSan 通常需要在构建阶段开启相应选项，并确保目标程序使用了兼容的运行库和符号信息。它适合测试构建、持续集成、回归测试和专项故障复现。与完整动态二进制插桩相比，LSan 在正常运行阶段的额外成本通常较低，但退出阶段仍需要进行根引用扫描和泄漏汇总，耗时会随对象数量和调用栈信息增长。

在工程评价中，LSan 应单独记录“是否需要重新编译”“检查发生在运行期间还是退出时”“是否需要保留符号”和“报告是否能还原到源码位置”。这些条件会直接影响它在生产环境、测试环境和跨平台构建中的适用范围。

## 3.3 基于运行时追踪的检测

基于运行时追踪的检测在程序已经启动后，通过动态库拦截、用户态探针或内核态 eBPF 探针观察分配和释放事件。它可以在不改变业务源代码的情况下附着到目标进程，按时间窗口输出当前仍在追踪的对象、字节数和主要调用路径。

运行时追踪通常强调“在线观察”和“较小接入成本”。它不会天然提供完整的进程退出可达性分析，结果更接近观察窗口内的状态快照或事件统计。快照时点、探针覆盖范围、采样比例、栈采集方式和运行库缓存都会影响最终数字。

### 3.3.1 BCC memleak

BCC memleak 是基于 eBPF 的用户态内存分配追踪工具。典型使用方式是在目标进程的 `malloc`、`calloc`、`realloc`、`free` 或相关分配器函数上挂载 uprobes，捕获分配返回地址、申请大小、线程和调用栈信息。部分追踪逻辑在内核中的 eBPF 程序内运行，分配状态通过 BPF map 保存，用户态程序再周期性读取并打印结果[[5]](https://github.com/iovisor/bcc/blob/master/tools/memleak.py)。

它的主要输出是 outstanding allocations，即观察时刻仍然处于追踪状态的分配。输出通常包括对象数量、总字节数、分配年龄或时间信息，以及按 stack ID 聚合的调用栈。对运行中的服务而言，这种输出可以快速回答“当前哪些调用路径积累了未释放对象”，也能通过连续快照观察数量和字节数是否增长。

### 3.3.2 配对、采样与快照时点

BCC memleak 可以维护地址级的分配/释放记录，但它的结果仍受观察机制影响。短生命周期对象可能在两次快照之间完成分配和释放，最终不会出现在快照中；没有被探针覆盖的分配路径不会进入状态表；分配器内部缓存可能让应用已经释放的对象继续以运行库状态存在。高频场景下，采样还可能减少事件处理压力，同时降低对短时对象的覆盖率。

因此，BCC memleak 的数字不能脱离采样窗口解释。实验中应同时记录启动时间、观察起止时间、快照间隔、探针函数、采样比例和过滤条件。对于 `growth_leak` 这类持续增长场景，应重点观察连续快照的增长趋势；对于 `definite_leak` 这类最终集合，应在负载完成后留出稳定观察窗口，再判断结果是否覆盖了预期对象。

### 3.3.3 其他运行时追踪工具

bpftrace 提供了更通用的 eBPF 脚本接口，可以通过 uprobes、uretprobes 和用户态栈追踪构建自定义的分配/释放统计。相较于预置工具，脚本可以自行定义过滤条件、聚合键和输出格式，但配对状态、异常路径、地址复用和清理逻辑也需要由使用者负责[[6]](https://github.com/bpftrace/bpftrace/blob/master/docs/language.md)。

这类工具适合在线筛查、热点路径发现、增长趋势观察和故障复盘。它们的工程优势来自可附着、可采样和可按需选择探针；工程限制来自内核版本、BPF 权限、符号化条件、调用栈深度和目标分配器实现。要把运行时追踪结果当作定量检测结论，必须明确输出对应的是完整事件集合、采样估计，还是某一时刻的 outstanding 快照。

## 3.4 基于 heap profiling 的画像分析

heap profiling 关注堆分配行为的整体画像。工具在运行期间记录分配、释放、对象大小、时间、线程和调用栈等信息，随后从 profile 中计算分配热点、峰值、临时对象、存活对象和增长路径。它的主要目标是帮助分析“内存从哪里来、何时增长、哪些调用路径贡献最大”，输出通常比单一的泄漏清单更丰富。

### 3.4.1 heaptrack

heaptrack 是 Linux 下的堆内存分析工具，通常通过启动包装或动态库拦截记录应用的分配和释放事件，并将事件与调用栈、时间和线程信息写入 profile 文件。随后可以使用命令行工具或图形界面分析 profile，查看分配热点、峰值内存、临时分配、泄漏候选和调用路径[[7]](https://github.com/KDE/heaptrack)。

heaptrack 的输出包括分配次数、分配字节数、释放字节数、峰值、存活分配和调用栈聚合结果。它可以把多个分配路径组织成画像，帮助分析哪类函数持续制造对象、哪条调用路径形成内存增长，以及高频分配是否主要来自短生命周期临时对象。对于复杂负载，画像视角比单独查看一个泄漏总量更容易解释内存变化过程。

### 3.4.2 与“泄漏判定”的关系

heaptrack 能提供泄漏候选和增长路径，但它首先是一种 profile 分析方案。最终结果依赖分析器对事件时间线、对象存活状态和调用栈的归并方式。一个对象在 profile 结束时仍未释放，可以被计入存活分配；它是否属于业务故障，还要结合负载预期、调用路径和程序生命周期判断。

使用 heaptrack 做 Benchmark 时，需要明确字节数的统计口径。报告中的 bytes 可能对应用户请求的字节数、分配器实际记录的字节数，或 profile 分析阶段经过单位转换和聚合后的字节数。不同工具的数字只有在解析规则统一后才适合横向比较。解析器还应区分 Benchmark 调用栈和运行库、线程库或工具自身的分配，无法明确归属的条目记录到备注中，避免直接计入检测结果。

### 3.4.3 工程特征

heaptrack 适合性能分析、内存增长诊断、热点路径定位和泄漏复盘。它保存的信息较多，profile 文件和后处理时间通常高于只输出汇总计数的工具。调用栈采集会增加运行开销，符号解析和源码定位效果依赖调试信息、编译选项及分析环境。

与只在进程退出时给出分类的工具相比，heaptrack 更容易呈现“分配热点、峰值、增长路径和对象生命周期”之间的关系；与在线快照工具相比，它更依赖完整事件记录和离线分析。因此它的适用场景偏向测试环境、性能分析和故障复盘，长期在线使用时需要通过采样、过滤和控制 profile 保存范围降低成本。

## 3.5 算法能力边界

四类方案使用的观测信号不同，检测结论的含义也不同。动态配对方案依靠实际分配和释放事件维护对象状态；编译期插桩方案通常在进程结束时基于根引用判断对象是否仍可达；运行时追踪方案提供选定窗口内的 outstanding 快照或趋势；heap profiling 方案保存更完整的分配画像，再通过后处理定位热点和增长路径。

### 3.5.1 能力对比

| 评价维度 | Valgrind Memcheck | ASan/LSan | BCC memleak / eBPF | heaptrack |
| --- | --- | --- | --- | --- |
| 主要判定依据 | 运行期对象状态与退出时可达性 | 插桩运行库记录的对象状态与退出时根引用扫描 | 探针覆盖范围内的 outstanding allocation 快照 | 分配事件时间线、存活对象和 profile 聚合 |
| 分配/释放配对 | 较完整，可结合地址和对象状态分析 | 运行库内部维护状态，用户输出以泄漏汇总为主 | 可做地址级配对，受探针、采样和状态清理影响 | 记录分配与释放事件，后处理时完成生命周期分析 |
| 泄漏规模量化 | 对象数和字节数较完整 | 可给出对象数和字节数，通常在退出时汇总 | 可给出快照时点的对象数和字节数 | 可给出存活量、峰值、分配量和路径聚合结果 |
| 持续增长观察 | 需要多轮运行或额外采样 | 需要多轮运行或额外检查点 | 适合连续快照和在线趋势观察 | 适合从时间线和画像中分析增长路径 |
| 调用栈定位 | 通常可到函数和源码行 | 通常可到函数和源码行 | 依赖 stack ID、符号和栈采集配置 | 通常可到函数和源码行，并支持路径聚合 |
| 运行开销 | 高 | 通常低于完整动态插桩，退出阶段有汇总成本 | 可控制，受事件频率、栈采集和输出窗口影响 | 中到高，取决于事件记录和 profile 规模 |
| 接入条件 | 以工具方式启动目标程序 | 通常需要重新编译或重新链接 | 需要 Linux 内核 BPF 能力和相应权限 | 通常以启动包装或动态库方式接入 |
| 典型场景 | 线下精确确认、回归测试 | 测试构建、持续集成、专项复现 | 在线筛查、趋势观察、热点发现 | 性能分析、增长诊断、故障复盘 |

### 3.5.2 检测效果的评价口径

如果 Benchmark 已经定义了每个 case 的真实泄漏对象数和字节数，可以把工具输出转化为统一结果。对于“是否检测到泄漏”的二分类结果，precision 表示工具报告的泄漏中有多少确实来自测试负载，recall 表示真实泄漏中有多少被工具报告。二者分别对应误报控制和漏报控制。

对于定量结果，还需要单独比较 detected_blocks 与 expected_blocks、detected_bytes 与 expected_bytes。对象数和字节数都匹配时，才能说明工具的规模统计口径与测试真值一致；只有分类正确而数量偏差较大时，应记录为“检测到，但量化口径存在差异”。对于调用栈，还要继续区分原始地址、函数名、源码位置和按调用栈聚合四个层级。

这套口径尤其适用于 BCC memleak 和 heaptrack。BCC 的结果需要绑定快照时点、观察窗口和探针配置；heaptrack 的结果需要说明字节单位、profile 统计范围和 Benchmark 调用栈筛选规则。Valgrind 和 LSan 的退出时报告也需要过滤运行库或工具自身引入的对象，避免把环境噪声混入 precision、recall 和字节数比较。

### 3.5.3 适用边界总结

Valgrind Memcheck 适合回答“这次运行具体泄漏了哪些对象”，代价是运行开销较重。ASan/LSan 适合放在测试构建和持续集成中，能够较快确认进程结束时仍无法解释的对象，接入时需要配合编译和链接。BCC memleak 适合在运行中的进程上观察 outstanding allocation 和增长趋势，结果必须结合探针覆盖和快照时点解释。heaptrack 适合建立堆分配画像，帮助定位热点、峰值和增长路径，结果分析依赖 profile 完整性和调用栈符号化。

因此，工具选择应由故障问题决定：需要一次精确确认时优先使用高完整性的线下检测；需要在测试流程中持续拦截问题时使用编译期插桩；需要观察运行中趋势时使用 eBPF 等运行时追踪；需要解释复杂内存变化和定位热点时使用 heap profiling。第五章将基于这些差异设计统一 Benchmark、结果解析规则和工程适用性指标，第六章再结合实验数据比较检测效果和开销。
