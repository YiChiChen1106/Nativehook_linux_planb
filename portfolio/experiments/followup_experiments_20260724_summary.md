# 7.16 组会后续实验汇总

## 一、本周完成内容

本周按照第八页的下一步实验安排，完成了四项工作：

1. 统一分析四个工具的原始输出，提取 expected/detected blocks、bytes、匹配状态、调用栈组数、Benchmark 泄漏栈命中、unknown 和 notes。
2. 补充调用栈定位分析，区分“能判断有无泄漏”和“能定位到 Benchmark 泄漏函数”。
3. 复核 BCC 的 attach 时机和结束后观察窗口，确认采集时序对结果的影响。
4. 完成线程、对象大小和迭代次数扩展实验，并把结果聚合成统一表格。

## 二、标准六类 case 的输出效果

标准实验使用四个工具、六类 case，每类重复 3 次。Valgrind、LSan、heaptrack 和 BCC memleak 在标准配置下的 blocks / bytes 均与 Benchmark 真值匹配，case-level 的匹配率均为 100%。

这里的 100% 说明标准配置下的泄漏存在性和数量判断符合预期。BCC 的运行库分配和 heaptrack 的非 Benchmark profile 条目仍保留在 `notes` 中，没有直接混入检测结果。

## 三、调用栈定位结果

四个工具在三个正样本 `definite_leak`、`growth_leak` 和 `mixed` 中都能命中 Benchmark 的泄漏函数，并能输出可识别的调用路径。当前结果可以概括为：

| 工具 | 调用栈输出 | Benchmark 泄漏栈 | 当前特点 |
| --- | --- | --- | --- |
| Valgrind | 有 | 3 类正样本均命中 | 泄漏记录和调用栈较直接，通常聚合为少量报告组 |
| LSan | 有 | 3 类正样本均命中 | 直接泄漏报告清晰，负样本通常没有泄漏栈 |
| heaptrack | 有 | 3 类正样本均命中 | profile 组较多，会同时看到运行库和输出相关分配 |
| BCC memleak | 有 | 3 类正样本均命中 | 能看到目标分配栈，但当前归属仍属于较粗粒度聚合，并会产生非负载栈 |

因此，四个工具都具备初步定位能力，但输出粒度不同。BCC 的 `notes` 中会保留未归属的运行库分配，heaptrack 会保留被过滤的 profile 条目，后续比较时需要把“定位到业务函数”和“输出了调用栈”分开记录。

## 四、BCC 时序对照

在 `growth_leak`、2 threads、4000 blocks / 256000 bytes 的负载下，进行了 attach 时机和结束后观察窗口对照。

| attach 条件 | 结束后观察窗口 | 结果 | 说明 |
| --- | ---: | --- | --- |
| 先 attach，再开始负载 | 7000 ms | 4000 / 256000 | 3 次重复均匹配 |
| 先 attach，再开始负载 | 9000 ms | 4000 / 256000 | 3 次重复均匹配 |
| 先 attach，再开始负载 | 12000 ms | 4000 / 256000 | 3 次重复均匹配 |
| 负载先开始，BCC 后 attach | 7000/9000/12000 ms | 0 或无归属结果 | 后续等待无法补回已错过的事件 |

这组实验说明，BCC 的关键控制点是覆盖分配过程。延长结束后的等待时间只能帮助观察已经被采集到的对象，不能恢复 attach 之前发生的分配。

## 五、线程和负载规模扩展

### 5.1 线程扩展

`definite_leak` 使用每线程 2000 次分配、单次 64 bytes。Valgrind、LSan 和 BCC 在 1、2、4、8 threads 下都完成精确匹配。heaptrack 在 1、2、4 threads 下匹配，8 threads 下 blocks 对上，bytes 稳定少报 4000。

`growth_leak` 中 BCC 能观察到随线程数增加的增长趋势，但数量低于理论值：

| threads | expected blocks | BCC 平均观测 blocks |
| ---: | ---: | ---: |
| 1 | 2000 | 1443 |
| 2 | 4000 | 2886 |
| 4 | 8000 | 5327 |
| 8 | 16000 | 11320 |

这表明 BCC 可以感知增长方向，但持续增长场景的完整计数仍然依赖快照覆盖范围和采样参数。

### 5.2 对象大小扩展

在 2 threads、每线程 2000 次分配下新增 256 bytes 和 1024 bytes 两组实验：

| 对象大小 | Valgrind | LSan | heaptrack | BCC |
| ---: | --- | --- | --- | --- |
| 256 bytes | 4000 / 1024000 | 4000 / 1024000 | 4000 / 1020000 | 4000 / 1024000 |
| 1024 bytes | 4000 / 4096000 | 4000 / 4096000 | 4000 / 4100000 | 4000 / 4096000 |

heaptrack 在两个规模下分别出现 -4000 和 +4000 bytes，blocks 始终为 4000。结合前面 8 threads 的复核结果，当前更适合把它记录为可读化显示和解析阶段的字节精度偏差，不能直接解释成实际分配少了或多了对象。

### 5.3 迭代次数扩展

在 2 threads、64 bytes 下将每线程迭代次数提高到 10000，理论值为 20000 blocks / 1280000 bytes。四个工具均得到 20000 / 1280000，说明本轮 heaptrack 偏差与对象数量增加没有简单的线性关系。

## 六、当前结论

本周工作已经从“能否检出泄漏”推进到“输出是否可解释、调用栈是否可定位、采样条件如何影响结果”。当前可以形成三条结论：

1. 标准六类 case 下，四个工具都能完成稳定的泄漏存在性判断，数量和字节数也能在标准规模下对齐。
2. BCC 的主要边界来自在线快照和采集时序。先 attach 再开始负载时，结果可以完整；持续增长过程中覆盖不足时，会出现稳定低估。
3. heaptrack 的 blocks 统计稳定，bytes 在部分规模下出现固定的显示/解析偏差；原始 profile 和人类可读输出需要分开解释。
