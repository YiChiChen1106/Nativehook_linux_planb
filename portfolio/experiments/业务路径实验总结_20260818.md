# 游戏业务路径 Benchmark 实验总结

## 新增 Case

本轮加入三类面向游戏负载的业务路径：

| Case | 模拟路径 | 设计的泄漏行为 |
| --- | --- | --- |
| `game_network_packet` | 网络包接收和处理 | 每 7 个包中保留 1 个异常包缓冲 |
| `game_audio_decode` | 音频解码和 PCM 缓冲扩容 | 每 6 次解码中保留 1 个失败路径的扩容缓冲 |
| `game_cache_eviction` | 资源缓存插入、淘汰和最终清理 | 最后一个缓存对象未被淘汰 |

## 实现内容

- benchmark 源码新增三类业务函数、worker、真值统计和 JSON case 信息。
- runner 新增 `business_paths` profile：2 线程、1200 次迭代、1024 bytes、3 次重复。
- 统一解析器补充三类调用栈归属规则，并为 heaptrack 增加缓存路径的栈回退规则。
- heaptrack 的 bytes 匹配允许 5 bytes 以内的显示舍入误差，原始误差仍保留在 `byte_delta` 和 `notes` 中。

## 首轮结果

四个工具分别运行 3 次。Valgrind、LSan 和 BCC 在音频解码、缓存淘汰上均与真值一致；网络包 case 中 BCC 有 1 次少观测 1 个 block，重复匹配率为 66.67%，其余两次一致。heaptrack 三类 case 的 blocks 和路径都稳定，bytes 仅出现 2 bytes 的 SI 单位显示误差，按显示误差规则计为匹配。

正式汇总见 `game_business_20260818_first/business_paths/formal_experiment_summary.md`。原始输出、真值文件和每次重复结果均保留在同一目录下。

## BCC 诊断

后续对网络包 case 做了单变量对照：把采样间隔从 2 秒改为 1 秒、把负载启动等待从 2 秒改为 5 秒，或把进程结束前等待从 8.5 秒改为 10 秒后，均能观测到完整的 342 个 block。由此可以确定问题与 BCC 的观测时序或窗口有关，但当前还不能单独归因到 attach 时机、采样间隔或事件捕获中的某一项；正式结论应写成“BCC 观测链路存在偶发少记录”，而不是确定为某一个具体原因。

随后对四种参数条件各重复 5 次：原始基线为 5/5 次得到 342 个 block，结束等待 10 秒为 5/5，采样间隔 1 秒为 5/5，启动等待 5 秒为 4/5。结合 BCC memleak 源码，工具的分配入口记录按“分配类型 + 线程号”保存，返回时如果找不到入口记录会直接跳过该分配；这提供了“入口/返回事件没有配对”的具体可能机制，但本轮还没有统计到该分支的命中次数，因此不能把它写成已经证实的根因。

## BCC 聚合链路定位

项目内新增 `tools/memleak_debug.py`，在 BCC 的入口缺失、调用栈采集失败和聚合表更新失败位置增加计数。对同一个 benchmark 进程同时运行两份 BCC：一份使用 `--combined-only`，另一份直接遍历地址表。抓到 341 blocks 的运行中，聚合输出为 341 个，但地址表输出为 342 个；三个 debug 计数均为 0。因此可以排除 `missed_alloc_entry` 作为这次少 1 个 block 的直接原因，问题已经定位到 `combined_allocs` 聚合统计路径，后续应重点检查并发更新、删除和按 stack_id 汇总时的状态一致性。

## 第二批边界 Case

本轮把四类容易影响实际游戏负载判断的边界加入 benchmark，每类都提供正常版和泄漏版：

| Case 组 | 模拟内容 | 主要观察点 |
| --- | --- | --- |
| `game_object_pool` | 对象池借用、归还，以及少量对象丢失 | 工具能否识别池化对象的最终归属 |
| `game_mmap` | 资源映射和 `munmap`，以及映射未释放 | 工具对非传统 heap 内存的覆盖范围 |
| `game_ui_callback` | UI 回调注册、取消，以及 owner/listener 互相持有 | 回调生命周期和引用环导致的残留 |
| `game_long_running` | 多轮运行，每轮释放临时对象或持续保留一条泄漏路径 | 周期快照能否观察到逐轮增长 |

新增 case 同时写入真值检查点：对象池使用 `after_load`、`after_cycle`，映射使用 `after_load`、`after_unmap`，UI 回调使用 `after_load`、`after_cancel`，长时间场景使用 `after_cycle_1`、`after_cycle_2` 等逐轮检查点。这样可以区分最终残留和运行中逐渐增长的路径。

## 第二批真值 Smoke

远端已同步并编译通过。以 2 线程、32 次迭代、128 bytes、3 轮为例：对象池泄漏版产生 8 blocks / 1024 bytes，映射泄漏版产生 64 blocks / 8192 bytes，UI 回调泄漏版产生 128 blocks / 16384 bytes，长时间泄漏版在三轮结束时累计 192 blocks / 24576 bytes；四个正常版的最终真值均为 0 blocks / 0 bytes，长时间泄漏版的检查点按 64、128、192 blocks 递增。

## 第二批工具 Smoke

缩小参数下四工具链路已完整跑通。对象池、UI 回调和长时间增长场景均能被 Valgrind、LSan、heaptrack 和 BCC 按预期识别；heaptrack 的个别字节数有 4 bytes 的 SI 显示舍入误差。`mmap` 泄漏版由 BCC 得到 16 blocks / 2048 bytes，Valgrind 和 LSan 没有给出可直接归入 heap 泄漏的结果，heaptrack 能看到映射相关记录但无法稳定还原 benchmark 字节数。这部分应作为方法能力边界记录，不能按普通 heap case 的标准强行判定。

本次 smoke 的统一表格保存在 `second_batch_smoke/summary.csv` 和 `second_batch_smoke/summary.md`；远端原始结果位于 `results/game_business_edges_smoke_20260818`。正式实验配置已加入 `business_edges` profile，后续可按正式参数和重复次数继续跑。

## 第二批正式配置单重复

已用 `business_edges` 正式 profile 完成 1 次全链路运行：2 线程、128 次迭代、4096 bytes、6 轮、4 个工具。对象池、UI 回调和长时间场景中，Valgrind、LSan 和 BCC 均与真值一致；heaptrack 的 blocks 能对上，但长时间场景字节数少 1456 bytes，UI 回调场景多 2848 bytes，属于 profile 输出的 SI 字节显示与聚合口径差异。`mmap` 泄漏场景仍由 BCC 精确得到 256 blocks / 1048576 bytes，Valgrind 和 LSan 保持 unknown，heaptrack 只报告 3 条映射相关记录且无法还原字节数。

这次结果说明第二批 case 已经完成“可运行、可解析、可比较”的第一版：正常版可以观察误报，heap 泄漏版可以比较块数和字节数，`mmap` 场景可以单独呈现非 heap 资源映射的工具边界，长时间场景可以检查按轮次增长。后续正式汇总需要单独记录 heaptrack 的字节口径。

## 第二批正式配置三次重复

已完成 3 次完整重复，配置仍为 2 线程、128 次迭代、4096 bytes、6 轮、4 个工具。四个正常版在 3 次运行中均为 100% 匹配；对象池泄漏版和 UI 回调泄漏版的 Valgrind、LSan、BCC 均为 3/3 匹配，长时间泄漏版三者也均为 3/3。BCC 对 `mmap` 泄漏版连续 3 次得到 256 blocks / 1048576 bytes，说明该场景在当前观察窗口下稳定可采集。

heaptrack 的块数在对象池、UI 回调和长时间场景均能对上，但字节数存在稳定口径差异：对象池为 -2 bytes，长时间场景为 -1456 bytes，UI 回调为 +2848 bytes；`mmap` 泄漏版三次均只能得到 3 条相关记录，字节数 unknown。这个结果进一步说明 heaptrack 的字节数需要单独按 profile 输出口径解释，不能直接与 benchmark 的申请字节数做完全相等判断。

三次重复的正式汇总保存在 `second_batch_formal_3rep_20260818/formal_experiment_summary.csv` 和 `second_batch_formal_3rep_20260818/formal_experiment_summary.md`；远端目录为 `results/game_like_blind/game_business_edges_formal_3rep_20260818`。
